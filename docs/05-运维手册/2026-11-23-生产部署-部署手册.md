# 生产部署手册

> 文档状态：现行
> 更新时间：2026-11-24
> 适用范围：在单台 Linux 主机上用 Docker Compose 安装 `ops-agent` 平台。
> 替代关系：替代 2026-11-23 版本。脚本参数以 `code/ops/deploy/README.md` 为准；两者冲突时先停手核对脚本，不要凭记忆执行。
> 路径说明：从 2026-11-24 起，标准安装位置为 `/data/ops-agent`，`/data` 建议单独挂一块盘。153 已于 2026-11-24 按该路径重新安装，旧 `/root/ops-agent` 已删除；后续 153 上的命令直接使用 `/data/ops-agent`，不要在同一个环境混用两套路径。

## 1. 一页速览

| 项目 | 当前值 |
| --- | --- |
| 安装目录 | `/data/ops-agent` |
| 启动文件 | `docker-compose.prod.yml` |
| 这套程序的名字 | `ops-agent`（不要再用 `ops-agent-prod`） |
| 安装入口 | `bash ops/deploy/deploy.sh` |
| 对外访问 | `http://<主机IP>:8080/` |
| 常驻程序 | `backend`、`worker`、`frontend`、`postgres`、`redis`、`minio` |
| 一次性程序 | `migrate`（建表、建账号、写初始数据）、`minio-init`（建桶） |
| 运行中的名字 | `ops-agent-backend-1`、`ops-agent-worker-1`、`ops-agent-frontend-1`、`ops-agent-postgres-1`、`ops-agent-redis-1`、`ops-agent-minio-1` |
| 数据库 | PostgreSQL 16 + pgvector，库名 `opsdb`，超级用户 `ops_root` |
| 文件存储 | MinIO，桶 `ops-agent-artifacts`、`ops-agent-screenshots`、`ops-agent-audit` |
| 任务队列 | PostgreSQL 的 `v3_task_queue` 表，不是 Redis 队列 |
| 管理员账号 | 默认 `admin`，密码取 `ADMIN_PASSWORD`；显示名“管理员” |
| 登录方式 | 账号密码 + 六位动态验证码；生产环境短信通道关闭 |

## 2. 先看清四条边界

1. **这是单机安装，不是高可用集群。** 一台机器同时跑网页、后台、跑任务的程序、数据库、缓存和文件存储；机器坏了，整套一起不可用。
2. **生产环境会真的执行。** 排查会读取真实数据源，审批通过后的处置会真的连目标机执行命令或跑模板。
3. **跑任务的程序不使用样例数据。** 没有真实数据源和主机时不会假装成功，只会如实报错。
4. **加密证书不在安装文件里。** 安装只对外提供 8080 的 HTTP；如果要用 HTTPS，需要在宿主机前面再加一层 Nginx 或负载均衡。

## 3. 最重要的一条规则：装新版本前先删干净旧平台

按现行要求，每次装新版本前，先把旧平台的**程序、程序文件、运行中的服务、安装目录、存放数据的目录**全部删掉，再装新的。

**这会删掉旧数据。** 只要旧环境里有需要保留的数据库、截图、报告或审计记录，必须先备份，再执行删除。没有备份就不要往下走。

机器上还没有旧平台时，跳过本节，只执行 `mkdir -p /data`，从第 4 节开始。

清理前先备份：

```bash
# 备份目录放在安装目录外面，不要在 /data/ops-agent 里面
mkdir -p /data/backups/$(date +%F)
cp -a /data/ops-agent/.env.production /data/backups/$(date +%F)/.env.production
cp -a /data/ops-agent/var/models /data/backups/$(date +%F)/models 2>/dev/null || true

# 数据库整库导出；旧环境还在运行时执行
TS=$(date +%Y%m%dT%H%M%S)
docker exec ops-agent-postgres-1 sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" --format=custom' \
  | gzip > "/data/backups/$(date +%F)/opsdb-${TS}.dump.gz"

# 确认压缩文件没坏，再往下走
gzip -t "/data/backups/$(date +%F)/opsdb-${TS}.dump.gz" && echo '数据库备份完整'
```

数据库备份命令和校验方法的完整说明见《日常运维手册》第 6 节；至少要把 `opsdb` 导出一份并确认能解开。旧环境的数据库容器不叫 `ops-agent-postgres-1` 时，先 `docker ps` 找到实际名字再替换；旧环境没有数据库就跳过这一步。

清理旧平台用脚本，不再手工逐条删：

```bash
# 如果这台机器现在仍装在 /root/ops-agent，把 cd 和上面的备份路径换成 /root/ops-agent
cd /data/ops-agent
bash ops/deploy/clean-platform.sh
```

脚本会先显示要删什么，要求输入 `DELETE` 确认；确认后执行。要跳过确认，加 `--yes`：

```bash
bash ops/deploy/clean-platform.sh --yes
```

旧安装目录里没有这个脚本时，从新部署骨架解压一份到临时目录再执行：

```bash
mkdir -p /tmp/ops-clean
tar -xzf ops-agent-deploy-<版本>.tar.gz -C /tmp/ops-clean
bash /tmp/ops-clean/ops/deploy/clean-platform.sh
```

脚本会清理：

| 对象 | 说明 |
| --- | --- |
| 容器 | 所有名字含 `ops-agent` 的容器 |
| 内部网络 | 所有名字含 `ops-agent` 的网络 |
| 数据卷 | 所有名字含 `ops-agent` 的 Docker 卷；加 `--keep-data` 时跳过 |
| 程序镜像 | `ops-agent-backend`、`ops-agent-worker`、`ops-agent-frontend` |
| 安装目录 | `/data/ops-agent`、`/root/ops-agent` 及已知旧测试目录 |
| 中间件数据 | `/data/ops-agent-data`；加 `--keep-data` 时跳过 |

脚本会保留：

- `/data/backups`，备份目录不动；
- 其他项目的容器、网络、卷、镜像和目录；
- 需要保留中间件数据时，加 `--keep-data`，脚本会保留 `/data/ops-agent-data` 和旧数据卷。

执行完脚本会打印设置文件备份位置。数据要留时，仍然要在执行脚本前先做数据库和附件备份。

## 4. 目标机要求

| 项 | 要求 |
| --- | --- |
| 系统 | x86_64 Linux，已验证 CentOS 7 |
| 内存 | 4 核 4G 可跑全栈；建议 4 核 8G |
| 磁盘 | 安装前至少留 8G 可用；建议整机 20G 以上 |
| Docker | Docker Engine + Compose v2，`docker compose version` 能正常输出 |
| 网络 | 能访问被管主机、日志平台和模型网关；默认还要能拉 PostgreSQL / Redis / MinIO 依赖镜像 |
| 时间 | 必须同步；动态验证码、任务租约、审计时间都依赖系统时间 |
| 端口 | 8080 可被访问；数据库、缓存、文件存储只走内部网络，不对外 |

## 5. 安装前检查

```bash
# 1. 系统和架构
uname -m
cat /etc/os-release

# 2. Docker 与 Compose
docker version
docker compose version

# 3. 内存和磁盘
free -h
df -h /

# 4. 8080 是否被占用
ss -lntp | grep ':8080' || true

# 5. 时间
timedatectl status 2>/dev/null || date
```

8080 被别的程序占用时，先查清是什么程序、能不能换端口；不要直接改端口硬启动。

### 5.1 准备 `/data`

安装目录统一放在 `/data` 下面，不放在 `/root`：

```bash
mkdir -p /data
chmod 755 /data
df -h /data
```

目录按下面分：

```text
/data
├── ops-agent/        程序和运行文件：启动文件、设置、模型、known_hosts
├── ops-agent-data/   中间件数据：postgres、redis、minio
├── backups/          数据库和设置备份，不要放进 ops-agent 里面
└── upload/           临时上传包，装完可以删
```

数据库、缓存和文件存储的数据已经绑定到 `ops-agent-data`，不再使用 Docker 命名卷。新建安装必须先在 7.3 节建好这三个目录并授权；迁移过程、权限和回退见 [中间件数据目录整改方案](2026-11-24-中间件数据目录整改方案.md)。

`/data` 最好是单独挂的一块盘。是单独盘时，按机房规范挂载到 `/data`，并写进 `/etc/fstab`，确保重启后还在；不要在没确认盘符的情况下直接格式化。

```bash
# 先看有哪些盘和分区
lsblk -f

# 挂载和写 fstab 按现场规范做，改完用下面两条确认
findmnt /data
df -h /data
```

如果 `/data` 只是根分区上的一个普通目录，那它只是换了个路径名，不能解决根分区被写满的问题；备份仍然要放到别的机器或 NAS。

注意：数据库、缓存、文件存储这三个服务的数据已经绑定到 `/data/ops-agent-data`，不再落 `/var/lib/docker`。Docker 的镜像、其他容器和构建缓存仍在 `/var/lib/docker`；如果连这部分也要放到 `/data`，需要改 Docker 的 `data-root`，这是影响整台机器所有容器的单独变更，必须停机确认，不要直接搬正在使用的目录。

## 7. 从零安装步骤

下面的命令都在目标机执行，安装目录用 `/data/ops-agent`。

### 7.1 放文件

```bash
mkdir -p /data/upload
# 把 ops-agent-<版本>.tar、docker-compose.prod.yml、deploy.sh、clean-platform.sh、.env.production.example 传到 /data/upload
ls -lh /data/upload
```

### 7.2 校验程序包

```bash
cd /data/upload
sha256sum ops-agent-<版本>.tar
```

与构建机给出的 SHA256 对不上就不要继续，重新传。

### 7.3 建安装目录

```bash
mkdir -p /data/ops-agent/ops/deploy /data/ops-agent/var/models /data/ops-agent/var/ssh
cp /data/upload/docker-compose.prod.yml /data/ops-agent/docker-compose.prod.yml
cp /data/upload/deploy.sh /data/ops-agent/ops/deploy/deploy.sh
cp /data/upload/clean-platform.sh /data/ops-agent/ops/deploy/clean-platform.sh
chmod +x /data/ops-agent/ops/deploy/deploy.sh /data/ops-agent/ops/deploy/clean-platform.sh

# 中间件数据目录；属主必须和容器用户一致
mkdir -p /data/ops-agent-data/postgres /data/ops-agent-data/redis /data/ops-agent-data/minio
chown 999:999 /data/ops-agent-data/postgres
chmod 700 /data/ops-agent-data/postgres
chown 999:1000 /data/ops-agent-data/redis
chmod 755 /data/ops-agent-data/redis
chown 0:0 /data/ops-agent-data/minio
chmod 755 /data/ops-agent-data/minio
stat -c '%u:%g %a %n' /data/ops-agent-data/postgres /data/ops-agent-data/redis /data/ops-agent-data/minio
```

### 7.4 放启动设置

从安全备份恢复 `.env.production`：

```bash
cp /data/backups/<日期>/.env.production /data/ops-agent/.env.production
chmod 600 /data/ops-agent/.env.production
```

第一次安装、没有现成设置文件时，从模板复制并逐项填写：

```bash
cp /data/upload/.env.production.example /data/ops-agent/.env.production
chmod 600 /data/ops-agent/.env.production
```

模板文件不在上传目录时，从源码仓库的 `code/.env.production.example` 取一份，不要凭记忆手写。

至少要确认这些值：

| 设置项 | 要求 |
| --- | --- |
| `COMPOSE_PROJECT_NAME` | `ops-agent` |
| `OPS_IMAGE_TAG` | 与导入的程序版本一致 |
| `EDGE_PORT` | 默认 `8080` |
| `POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` | 超级用户、密码、库名；库名默认 `opsdb` |
| `DB_APP_ROLE` / `DB_APP_PASSWORD` | 应用读写账号，不能和超级用户共用 |
| `DB_AUDIT_READER_ROLE` / `DB_AUDIT_READER_PASSWORD` | 审计只读账号 |
| `DB_AUTH_ROLE` / `DB_AUTH_PASSWORD` | 登录认证账号 |
| `DB_USER_ADMIN_ROLE` / `DB_USER_ADMIN_PASSWORD` | 用户管理账号 |
| `AUTH_TOKEN_SECRET` | 至少 40 个字符；丢了所有登录失效 |
| `TOTP_ENCRYPTION_KEY` | 动态验证码加密密钥；丢了已绑定的验证码解不开 |
| `CREDENTIAL_ENCRYPTION_KEY` | 数据源和模型密钥的加密密钥；不能和上面共用 |
| `EXEC_PERMIT_SECRET` | 至少 40 个字符；一次性执行许可依赖它 |
| `ADMIN_USERNAME` / `ADMIN_PASSWORD` | 默认账号 `admin`；密码首次登录后要改 |
| `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` | 文件存储管理账号 |
| `MINIO_USER` / `MINIO_PASSWORD` | 应用使用的账号 |
| `ALERT_WEBHOOK_TOKEN` | 告警接入令牌；不填告警会被拒 |
| `CORS_ORIGINS` | 实际访问地址；不要留 `localhost` |
| `SMS_CHANNEL` | 只用密码 + 动态验证码时填 `disabled`，不能填 `test` |
| `SSH_HOST_KEY_POLICY` | 建议 `strict` 或 `prompt`，不要用 `off` |

生成随机值：

```bash
# 数据库密码、管理员密码、文件存储密码
openssl rand -hex 24

# 三个长令牌
openssl rand -hex 32

# 两个加密密钥
openssl rand -base64 32 | tr '+/' '-_' | tr -d '\n'
```

检查有没有忘记替换的模板值：

```bash
grep -nE 'CHANGE_ME|REPLACE_ME' /data/ops-agent/.env.production || echo '没有模板占位值'
```

### 7.5 放模型和主机公钥文件

```bash
# 模型：有就放，没有也能启动，只是语义检索退回关键词检索
mkdir -p /data/ops-agent/var/models
# 把 bge-small-zh-v1.5 整个目录放到 /data/ops-agent/var/models/
test -f /data/ops-agent/var/models/bge-small-zh-v1.5/model.onnx && echo '模型就位'

# 主机公钥登记文件必须是普通文件，不能是目录
: > /data/ops-agent/var/ssh/known_hosts
chmod 666 /data/ops-agent/var/ssh/known_hosts
```

`known_hosts` 里只存目标机的公钥，不放私钥或密码。设成 666 是因为后台和跑任务的程序用不同用户运行，两边都要能写；安装目录本身必须只有 root 能进，不能把这个文件暴露给其他账号。

### 7.6 导入程序

```bash
cd /data/ops-agent
docker load -i /data/upload/ops-agent-<版本>.tar
docker image ls --format '{{.Repository}}:{{.Tag}} {{.Size}}' | grep ops-agent
```

必须看到三个：

```text

ops-agent-worker:<版本>
ops-agent-frontend:<版本>

### 7.7 依赖程序

数据库、缓存、文件存储的依赖程序默认由安装脚本从镜像站拉取。目标机不能联网时，先在能联网的机器导出这四个，再传进来：

docker save -o base-images.tar \
  docker.1ms.run/pgvector/pgvector:0.8.0-pg16 \
  docker.1ms.run/library/redis:7.4.12-alpine \
  swr.cn-north-4.myhuaweicloud.com/ddn-k8s/docker.io/minio/minio:RELEASE.2025-03-12T18-04-18Z \
  swr.cn-north-4.myhuaweicloud.com/ddn-k8s/docker.io/minio/mc:RELEASE.2025-03-12T17-29-24Z

# 目标机
docker load -i base-images.tar
# 并在 .env.production 里设置 OPS_PULL_BASE_IMAGES=0
```

### 7.8 执行安装

```bash
cd /data/ops-agent
bash ops/deploy/deploy.sh < /dev/null
```

末尾的 `< /dev/null` 不能省。安装脚本里有一条 `docker compose run` 会读输入；不加这个重定向，它会把后面的输入吞掉，安装会在中途停住。这个问题已经实际遇到过，不是理论风险。

正常情况下会看到：

1. 检查启动设置里的必填值、占位值、密钥长度；
2. 校验启动文件；
3. 检查三个程序都在；
4. 启动数据库、缓存、文件存储；
5. 跑一次性初始化：37 份建表改动、账号、初始数据、归档设置、凭据设置、7 个操作模板；
6. 启动后台、跑任务的程序、网页；
7. 最多等 180 秒，直到本机 `/api/health` 返回正常。

看到 `[deploy] 完成：http://<宿主机IP>:8080/` 才算装完。

### 7.9 首次登录

浏览器打开 `http://<主机IP>:8080/`，账号是 `admin`，密码是 `.env.production` 里的 `ADMIN_PASSWORD`。

登录后马上做三件事：

1. 改管理员密码；
2. 绑定动态验证码；
3. 建日常使用的个人账号，不要把管理员账号长期共用。

## 8. 安装后必须检查

### 8.1 程序状态

```bash
cd /data/ops-agent
docker compose --env-file .env.production -f docker-compose.prod.yml ps -a
```

期望：`ops-agent-postgres-1`、`ops-agent-redis-1`、`ops-agent-backend-1`、`ops-agent-frontend-1` 是 `healthy`，`ops-agent-worker-1` 是 `Up`；`migrate`、`minio-init` 是正常退出。

### 8.2 页面和后台

```bash
curl -fsS http://127.0.0.1:8080/api/health
```

期望：

```json
{"status":"ok","service":"backend","environment":"production"}
```

再打开首页，返回 200。

### 8.3 管理员账号

```bash
docker exec -i ops-agent-postgres-1 sh -c \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select id, username, display_name, roles from v3_users order by id;"'
```

期望看到 `admin / 管理员 / {admin}`，以及 `system-alert / 系统告警 / {investigator}`。

### 8.4 设置和模板

```bash
docker exec -i ops-agent-postgres-1 sh -c \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select namespace, key from v3_configs order by 1,2;"'
```

必须包含：

- `archive / default`（归档设置，安装时自动写入，不需要手工补）
- `credentials / default`（凭据设置）
- 7 个 `deploy_template`

### 8.5 队列和磁盘

```bash
docker exec -i ops-agent-postgres-1 sh -c \
  'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "select status, count(*) from v3_task_queue group by 1;"'

df -h /
docker system df
```

刚装完队列应为空；磁盘至少留 4G 余量。

### 8.6 日志

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml logs --tail=100 backend worker frontend
```

重点看：后台没有数据库连接失败、密钥缺失；跑任务的程序没有模型/凭据/主机公钥报错；网页没有 502。

### 8.7 审计维护定时任务

查看 cron 文件：

```bash
cat /etc/cron.d/ops-agent-audit
```

应看到每天 00:05 以部署用户执行 `docker compose run` 的配置。

手动跑一次：

```bash
sudo -u opsagent bash -lc 'cd /data/ops-agent && /usr/bin/docker compose --env-file .env.production -f docker-compose.prod.yml run --rm --no-deps -T backend python scripts/audit_maintenance.py'
```

退出码 0 表示缓冲补写、归档和校验都成功。状态文件在 `var/audit-archive/maintenance-status.json`，日志在 `var/logs/audit-maintenance.log`。

没有 cron 文件时执行：

```bash
sudo bash ops/deploy/install-audit-maintenance.sh
```

## 10. HTTPS 和反向代理

安装本身只提供 8080 的 HTTP。需要 HTTPS 时，在宿主机前面加 Nginx 或负载均衡，由它管证书，再把请求转到 `127.0.0.1:8080`。

```nginx
server {
    listen 443 ssl;
    server_name ops.example.com;

    ssl_certificate     /etc/nginx/certs/ops.example.com.pem;
    ssl_certificate_key /etc/nginx/certs/ops.example.com.key;

    location / {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # 任务过程是长连接，不能缓冲，否则页面看起来卡住
        proxy_buffering off;
        proxy_read_timeout 300s;
    }
}
```

注意：

- `proxy_buffering off` 必须保留；
- `CORS_ORIGINS` 要写实际域名；
- 不要在反向代理里再改 `/api` 路径；
- 不要把 8080 直接暴露到公网。

## 11. 告警接入

Alertmanager 的 Bearer 令牌要和启动设置里的 `ALERT_WEBHOOK_TOKEN` 一致：

```yaml
receivers:
  - name: ops-agent
    webhook_configs:
      - url: http://<ops-agent-host>:8080/api/alerts/alertmanager
        send_resolved: true
        http_config:
          authorization:
            type: Bearer
            credentials: <ALERT_WEBHOOK_TOKEN>
```

| 返回码 | 含义 | 处理 |
| --- | --- | --- |
| `202` | 已接收 | 正常 |
| `401` | 令牌不一致 | 核对两边令牌 |
| `413` | 告警内容超过大小限制 | 调整告警内容，不要盲目放大限制 |
| `503` | 没配令牌 | 补令牌并重建后台程序 |

先用一条明确写着“接入测试”的告警确认能生成任务，再备注测试来源。

## 12. 升级、重装和回退

### 12.1 默认方式：删干净再装

按第 3 节执行：先备份，再运行 `clean-platform.sh`，然后从第 7 节装新版本。

适合：业务数据不需要保留，或已经备份并准备恢复。

### 12.2 要保留旧数据时

这是例外，必须单独确认。

1. 导出 `opsdb` 并校验；
2. 备份 `ops-agent-artifacts`、`ops-agent-screenshots`、`ops-agent-audit` 三个桶；
3. 运行 `bash ops/deploy/clean-platform.sh --keep-data`，保留 `/data/ops-agent-data` 和旧卷；
4. 按第 7 节装新版本，让初始化脚本在旧库上继续跑；
5. 如果新版本改了表结构，先确认迁移兼容，再启动。包含评论线索、逐条报告反馈和审批值班的版本，要按《平台使用操作手册》第 13 节顺序执行 `038`、`039`、`040` 三个迁移；回滚按 `040`、`039`、`038` 倒序执行，回滚前先导出反馈和值班记录。

数据目录现在固定为 `/data/ops-agent-data`，不再跟 Docker 项目名走；`--keep-data` 会跳过这个目录和旧卷。没有备份、没有确认，不要走这条。

### 12.3 回退

因为每次都删旧程序文件，回退不能指望机器上还有旧版本。必须提前把旧版本的完整程序包和数据库备份放在机器外面。

回退步骤：

```bash
# 1. 清理当前程序和容器，保留数据目录和旧卷，便于恢复
bash ops/deploy/clean-platform.sh --keep-data

# 2. 按第 7 节装回旧版本
# 3. 数据库恢复按《日常运维手册》第 6 节执行
```

只回退程序、不回退数据库，可能因为表结构不一致起不来。

临时停机：

```bash
cd /data/ops-agent

```

全部停止：

```bash
docker compose --env-file .env.production -f docker-compose.prod.yml stop
```

彻底卸载（会删数据，先备份）：

```bash
bash ops/deploy/clean-platform.sh

bash ops/deploy/clean-platform.sh --yes
```

脚本会删除容器、网络、旧卷、程序镜像、安装目录和 `/data/ops-agent-data`，保留 `/data/backups`。

## 14. 常见失败原因

| 现象 | 先查什么 | 怎么处理 |
| --- | --- | --- |
| 远程连不上主机 | 虚拟机或物理机是否开机、网络是否通 | 先开机，再查网络 |
| 磁盘不够，导入失败 | `df -h /` | 删旧程序文件、清构建缓存，至少留 8G |
| `缺少镜像 ops-agent-backend:<版本>` | `docker image ls`、`OPS_IMAGE_TAG` | 重新导入程序包，或把版本号改对 |
| 提示 `CHANGE_ME` / `REPLACE_ME` | `.env.production` | 把所有模板值替换掉 |
| 新装后用到旧数据库 | 启动文件第 6 行、`COMPOSE_PROJECT_NAME` | 两边都必须是 `ops-agent` |
| 提示缺 `archive/default` | 初始化步骤里有没有 `init_audit_v3.py --seed-only` | 当前版本已自动写入；没有就补上这一步 |
| 报 `No module named 'paramiko'` | 后台程序打包清单 | 补 `paramiko>=3,<6` 并重新打包后台程序 |
| 初始化跑一半停住 | 是否用管道把脚本送过去执行 | 安装命令后面加 `< /dev/null`；内部命令加 `-T` |
| `known_hosts 必须是普通文件` | `var/ssh/known_hosts` | 删掉误建的目录，执行 `: > var/ssh/known_hosts`，再重跑 |
| 180 秒页面还不正常 | `ps`、后台和网页日志 | 看后台是否起来、数据库能否连、网页是否 502 |
| 页面能开但接口 502 | 后台容器状态和日志 | 先解决后台退出原因，不要只重启网页 |
| 告警 503 | `ALERT_WEBHOOK_TOKEN` | 补令牌并重建后台程序 |
| 管理员登录名不对 | `ADMIN_USERNAME`、`v3_users` | 默认是 `admin`；旧名 `ops_admin` 已不再使用 |

## 16. 裸机 Linux 直接部署（systemd）

> 本节只适用于不使用 Docker Compose 的裸机部署。已经按第 1 至 15 节用容器部署的机器，不要再装这两个服务，容器里的 `worker` 已经由 `restart: unless-stopped` 守护。

裸机部署至少有两个 Python 常驻进程，必须分开管理：

- `ops-agent-api.service`：网页接口和后端任务提交；
- `ops-agent-worker.service`：从队列领取排查、部署、命令执行和知识整理任务。

`worker` 不是 `uvicorn` 的子进程。只重启 API 不会拉起 worker，任务会一直停在 `draft/queued`，页面显示“AI 排查准备中”。

两份可复制的服务文件已放在 `code/ops/deploy/systemd/`：

- `ops-agent-api.service`
- `ops-agent-worker.service`

也可以按下面内容手工写入。

### 16.1 运行用户和目录

以下示例按代码目录 `/data/ops-agent/code`、运行用户 `opsagent` 编写；实际路径和用户不同时，逐字替换。如果代码直接放在 `/data/ops-agent` 下，把下面所有 `/data/ops-agent/code` 换成 `/data/ops-agent`。

```bash
sudo useradd --system --home /data/ops-agent --shell /usr/sbin/nologin opsagent
sudo chown -R opsagent:opsagent /data/ops-agent/code
```

### 16.2 API 服务

写入 `/etc/systemd/system/ops-agent-api.service`：

```ini
[Unit]
Description=Ops Agent Backend API
After=network-online.target postgresql.service redis.service
Wants=network-online.target

[Service]
Type=simple
User=opsagent
Group=opsagent
WorkingDirectory=/data/ops-agent/code/backend
EnvironmentFile=/data/ops-agent/code/.env
ExecStart=/data/ops-agent/code/backend/.venv/bin/python -m uvicorn app.main:app --host 0.0.0.0 --port 8000
Restart=always
RestartSec=5
TimeoutStopSec=30
UMask=0027
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

### 16.3 队列 worker 服务

写入 `/etc/systemd/system/ops-agent-worker.service`：

```ini
[Unit]
Description=Ops Agent Queue Worker
After=network-online.target postgresql.service redis.service
Wants=network-online.target

[Service]
Type=simple
User=opsagent
Group=opsagent
WorkingDirectory=/data/ops-agent/code
EnvironmentFile=/data/ops-agent/code/.env
ExecStart=/data/ops-agent/code/backend/.venv/bin/python backend/scripts/run_queue_worker.py --interval 5
Restart=always
RestartSec=5
KillSignal=SIGINT
TimeoutStopSec=120
UMask=0027
NoNewPrivileges=true
PrivateTmp=true

[Install]
WantedBy=multi-user.target
```

### 16.4 启动和自检

如果直接使用仓库自带模板，先复制：

```bash
sudo install -m 0644 /data/ops-agent/code/ops/deploy/systemd/ops-agent-api.service /etc/systemd/system/
sudo install -m 0644 /data/ops-agent/code/ops/deploy/systemd/ops-agent-worker.service /etc/systemd/system/
```

再加载并启动：

```bash
sudo systemctl daemon-reload
sudo systemctl enable --now ops-agent-api ops-agent-worker
sudo systemctl status ops-agent-api ops-agent-worker
```

查看 worker 是否真正在领取任务：

```bash
journalctl -u ops-agent-worker -f
```

期望日志里出现 worker ID 和轮询记录；队列有任务时会出现 `"claimed": true`，任务状态从 `queued` 变成 `running`。

检查接口：

```bash
curl -fsS http://127.0.0.1:8000/api/public/login
```

检查队列：

```bash
psql "$DATABASE_URL" -c \
  "select status, count(*) from v3_task_queue group by 1;"
```

### 16.5 使用限制

- `EnvironmentFile` 里的 `.env` 必须是普通 `KEY=VALUE`，不要写 `export`，也不要在值后面加行内注释；否则 systemd 可能读不到变量。
- 示例里的 `After=postgresql.service redis.service` 只适用于数据库和缓存装在同一台机器的情况；如果是外部数据库，改成实际服务名，或删掉不存在的依赖。
- `worker` 会跑几分钟的长任务，`TimeoutStopSec=120` 是留给它收尾的时间，不要改得太短。
- 前端如果是 Vite 构建产物，应由 Nginx 等静态服务托管；这两个 systemd 服务只负责 API 和队列 worker。
- 裸机多 worker 可以同时启动，队列领取使用 `FOR UPDATE SKIP LOCKED`，不会重复领取同一条任务；一般一台机器启动一个即可。
