# 平台使用操作手册

> 文档状态：现行
> 更新时间：2026-11-25
> 适用范围：平台页面操作、飞书通知与群命令、审批与部署。
> 适用读者：一线值班工程师、排查员、管理员、审计员和只读查看人员。
> 说明：页面按钮会按角色显示，真正的权限以后台接口为准。本手册按实际导航顺序写，不把“报告完成”写成“已经采纳”。
> 截图说明：截图来自本地演示环境，主机地址、任务和账号均为演示数据，不是生产环境数据。

## 1. 角色与能看到的东西

| 角色 | 页面上的名称 | 主要能做什么 |
|---|---|---|
| `admin` | 管理员 | 审批、执行、配置、用户管理、主机管理、部署方案确认和查看 |
| `investigator` | 排查员 | 新建排查、看报告、提交处置方案、创建部署方案 |
| `oncall` | 值班工程师 | 新建排查、看报告、提交处置方案、处理分配到的任务 |
| `auditor` | 审计员 | 查审计、看任务和知识库、导出审计流水 |
| `viewer` | 只读 | 查看授权范围内的页面，不能改配置、不能审批执行 |

导航分两组：

- 业务：工作台、排查、部署、知识库、审批、审计；
- 管理：主机、配置。

看不到某个入口，通常不是页面坏了，而是当前角色没有对应权限。

## 2. 登录与账号安全

打开 `http://<平台地址>:<端口>/`，输入账号和密码。

生产默认是“密码 + TOTP”，不依赖短信验证码：

1. 输入账号、密码；
2. 输入 6 位动态口令；
3. 首次登录或管理员重置后，按页面提示绑定 TOTP；
4. 绑定成功后把恢复方式放在受控位置，不要截图发聊天工具。

注意：

- 连续输错会触发登录锁定，等待期内不要反复试；
- 不要把 TOTP 二维码、密钥或密码发给他人；
- 公共电脑用完点退出，不要只关浏览器标签；
- 页面顶栏会显示当前登录账号和角色，发现不是自己的账号先退出。

## 3. 工作台

工作台是入口页，主要看：

- 最近排查和待处理事项；
- 数据源状态：哪些数据源可用、哪些异常；
- 快捷输入框：可以直接描述现象发起排查。

![工作台总览：任务量、待处理项和快捷入口](images/01-工作台.png)

生产环境请按部署配置和后台健康检查确认，不要只看页面外观；具体核对方法见《生产部署手册》。

## 4. 新建排查

### 4.1 入口

导航“排查” → “新建排查”，或工作台快捷输入框。

新建页只有一个自然语言入口，不需要先选工具或填一堆参数。

![新建排查：一句话描述、示例和报错截图入口](images/02-新建排查.png)

### 4.2 描述怎么写

输入框提示是“用一句话描述现象”。实际写的时候，建议把四件事说清：

1. **时间**：从什么时候开始，是否持续；
2. **对象**：哪台主机、哪个服务、哪个集群；
3. **现象**：报错、变慢、不可用、掉线、磁盘满等；
4. **范围**：只影响一个实例，还是整个环境；有没有已知变更。

示例：

```text
今天 10:05 开始，订单服务在 ops-host-1 上响应变慢，P99 从 80ms 升到 2s，
只影响这一台，10:00 前后没有发布。帮我查指标、日志和主机状态。
```

不要只写“系统挂了”“帮我看看”。Agent 会在报告里把“缺目标、缺数据”的部分标出来，但描述越具体，证据越容易对上。

### 4.3 上传报错截图

可以点“上传报错截图”或把图片拖进输入区。

平台会先做 OCR，把识别结果作为“人工截图”证据进入报告。注意：

- OCR 不是原文，关键字段以原图为准；
- 截图里如果有密码、令牌、身份证、手机号，先打码；
- 截图只是补充证据，不能代替指标和日志；
- 不要上传与本次现象无关的聊天截图。

### 4.4 提交

点“开始排查”。提交后任务进入队列，状态从“已提交”变成“进行中”。

提交后会发生：

1. Agent 按描述拆排查步骤；
2. 查指标、日志、主机状态，边查边把证据挂到任务上；
3. 生成报告，写结论、证据和“还没确认”的部分；
4. 只有需要改机器、跑命令时，才进入“待审批”。

### 4.5 状态怎么读

| 页面状态 | 含义 | 你要做什么 |
|---|---|---|
| 已提交 | 已入队，还没被 worker 领取 | 等；长时间不动看队列 |
| 进行中 | Agent 正在排查 | 可在“过程与参考”看实时事件 |
| 报告已完成 | 报告和证据已生成 | 读结论和证据；这不等于“已采纳” |
| 待审批 | 已有人提交处置方案，等管理员批准 | 管理员审命令；提交人不能当批准人时按页面提示走 |
| 执行中 | 命令正在目标机执行 | 看执行结果，不要重复点 |
| 已结束 | 终态，结果写在 outcome | 需要重来只能新建任务 |

**报告已完成 ≠ 已采纳。** 平台没有单独的“采纳状态”；“采纳”是任务结束后的 outcome 之一。报告只是结论，执行是另一条链路。

![排查列表：按状态、处理人、类型和时间筛选](images/03-排查列表.png)

## 5. 看报告与证据

打开“排查” → 点任务标题进入“排查详情”。

详情页有四个标签：

![排查详情：状态、转派、报告导出和四个标签](images/04-排查详情-结论.png)

### 5.1 结论

先看结论要点、关键事实和根因判断。

重点辨别：

- 哪些结论有证据支持；
- 哪些只是假设，页面会写“证据不足”；
- 哪些部分写“无数据”或“未知存量”。

“无数据”不是“正常”。没有拿到数据时，正确结论是“没查到”，不是“没问题”。

### 5.2 处置方案

这里展示报告给出的可执行建议。注意：建议不是命令，不能直接当审批方案。

要执行时，回到详情页点“创建处置方案”，由人填写目标、命令和说明。

### 5.3 证据

证据按主机或来源分组，每条有 `evidence_id`。结论里引用的证据可以点回原文。

看证据时确认：

- 时间和主机对不对；
- 命令或查询是不是这次真实执行的；
- 数据质量是“有数据”“无数据”还是“未知存量”；
- 截图 OCR 和原图是否一致；
- 历史知识是否被误当成本次证据。

历史报告只做参考，不能直接当本次结论。

![证据标签：按结论点回原文，区分有数据、无数据和未知存量](images/05-排查详情-证据.png)

### 5.4 过程与参考

这里看 Agent 的排查过程事件、工具调用和参考知识。

用途：

- 判断 Agent 是不是查了正确的主机和服务；
- 看它为什么停下来、缺了哪个数据源；
- 交接时说明“查到哪里、还差什么”。

### 5.5 报告导出、评论和转派

- **报告导出**：详情页右上角有“报告导出”，导出的是这次报告和证据，不是审批单；
- **评论**：可以留结论、补充现场信息或交接说明，支持 `@用户名` 提醒；评论可撤回，正文不能编辑；
- **作为排查线索**：写评论时勾选“作为排查线索”，下一次 Agent 排查会读取这条内容；普通讨论不会进入 Agent。线索只作参考，评论里的命令、地址和步骤不会被直接执行；与现场证据冲突时以证据为准；
- **逐条反馈**：根因判断和“发现与验证”里的每条结论下都有“准确 / 不准确 / 纠正”，按当前登录人分别保存，同一位置再次提交会覆盖自己的旧反馈；
- **转派**：点“转派”，选择接手人；转派只换处理人，不改变任务状态和证据；
- **撤回排查**：只对还没进入执行的排查有效；已经执行的不能靠“撤回”当回滚。

## 6. 从报告走到执行

### 6.1 什么时候需要处置

只有需要改机器、跑命令、重启服务、改配置时，才需要创建处置方案。

只是看报告、做结论、转派、评论，不需要审批。

### 6.2 创建处置方案

在排查详情点“创建处置方案”，填写：

| 字段 | 怎么填 |
|---|---|
| 执行目标 | 选平台里已登记的主机；填 `local` 或主机 ID；未登记主机会被拒绝 |
| 命令 | 一条命令一行；不要管道、重定向、`&&` 或 `;` 组合，平台只执行 argv |
| 说明 | 为什么需要处置、影响范围、失败时怎么办；审批人会看到 |

至少一条命令才能提交。提交后状态进入“待审批”，**批准前不会执行**。

命令写法示例：

```text
systemctl status nginx
journalctl -u nginx -n 100 --no-pager
df -h
```

不要写：

```text
systemctl restart nginx && curl localhost
cat /var/log/nginx/error.log | grep timeout
```

平台不解析 shell 管道和组合符；写了也不会按你想象的方式执行。

### 6.3 审批页

导航“审批”只对管理员开放。审批详情有三个分组：

- **结论**：看这次排查的结论和证据，判断命令有没有依据；
- **命令与审批**：看目标主机、命令、说明、回滚和风险；
- **执行结果**：批准后看状态、退出码和输出预览。

审批时要做：

1. 先看结论和证据，不看“AI 预审”就批准；
2. 核对目标主机是不是生产、命令是不是最小必要；
3. 核对说明里的影响范围和失败处理；
4. 输入 6 位 TOTP；
5. 点“批准并执行”，或“驳回”。

“AI 预审（不代替人工批准）”只是辅助，不是批准依据。AI 说低风险，也不等于可以跳过人工核对。

![审批页：待审批队列和可回看的审批记录](images/06-审批记录.png)

### 6.4 驳回、撤回和终止

- **驳回**：任务结束，outcome 为 `rejected`；报告和证据保留；
- **撤回**：只对还没执行的处置有效；
- **终止执行**：执行中可请求终止；已经发出的命令可能已产生部分影响，终止后仍要核对执行结果和审计。

不要用“驳回”掩盖执行失败，也不要用“终止”代替回滚。

### 6.5 执行结果

批准后看：

- 状态：执行中 / 已结束；
- 结果：`succeeded`、`failed`、`partial` 等；
- 退出码和输出预览；
- 审计记录里的完整链路。

`exec` 类命令失败不会自动重试，因为可能已经产生副作用；需要人工核对后重新发起。

## 7. 部署

导航“部署”有三个页签：

| 页签 | 用途 |
|---|---|
| 新建部署 | 用 AI 生成方案，或从模板库选模板 |
| 部署记录 | 看历史方案、审批、执行、验证和回滚 |
| 模板库 | 管理已发布模板和模板版本 |

![部署页：新建部署、自主生成方案和从模板库选择](images/07-部署页.png)

### 7.1 两种创建方式

**自主生成方案**：

- 填“要部署什么”、目标主机、部署类型；
- AI 生成结构化步骤；
- 命令由后端解析 argv 并过允许/禁止清单；
- 审批前不会执行。

**从模板库选择**：

- 选一个已发布模板；
- 填目标主机、部署类型、标题；
- 命令、验证、回滚和 `plan_hash` 由模板确定性生成，不是模型现场编命令。

规划失败不会“套模板兜底”；任务会关闭并保留过程，可以改用模板创建。

### 7.2 方案确认

方案生成后，页面显示方案指纹 `plan_hash`。确认流程：

1. 核对模板版本、目标主机、命令、验证和回滚；
2. 点“我确认这份方案”；
3. 只有提交人可以确认；
4. 确认后进入待审批，批准需要一次性令牌。

方案有 TTL，过期后不能确认或批准，只能重新生成或驳回关闭。

### 7.3 审批与执行

- 默认职责分离：自己提交的部署任务，默认不能自己批准；
- 批准需要一次性令牌和 TOTP；
- 审批页不重新录入命令，避免绕过 `plan_hash`；
- 执行后看验证结果和回滚结果。

不要为了赶时间打开“自审批豁免”。自审批清单可检索、可统计、可导出；是否允许自审批是管理决策，不是操作捷径。

### 7.4 部署失败

看“部署记录” → 选中任务：

- 失败原因；
- 实际执行的规划步骤；
- 验证结果；
- 回滚结果和回滚后验证。

![部署记录：方案指纹、审批链、执行结果和失败原因](images/08-部署记录.png)

回滚失败要按事故处理，不能只写“已回滚”。

## 8. 主机

导航“管理” → “主机”。

![主机列表：启用状态、地址和编辑/更多操作入口](images/11-主机列表.png)

### 8.1 新增主机

点“新增主机”，填写：

| 字段 | 说明 |
|---|---|
| 主机 ID | 例如 `ops-host-1`；创建后不可改 |
| 平台 | 物理机、虚拟机、容器等 |
| 操作系统 | 决定能跑 `apt` 还是 `dnf/yum` |
| 系统名称/版本 | 例如 `centos` / `7.9` |
| 包管理器/服务管理器 | 例如 `yum` / `systemd` |
| 地址/端口 | SSH 地址和端口 |
| 账号 | SSH 登录账号 |
| 登录密码 | 只写不读；编辑时留空表示保留原密码 |
| 启用 | 启用前必须已配置登录密码 |

保存后回到主机列表，点“确认密钥”。

### 8.2 主机公钥

平台只做 SSH 握手取公钥，管理员到目标机控制台核对指纹后再登记。

- 默认策略 `prompt`：首次未登记可确认；
- `strict`：只认已登记主机，未登记直接失败；
- `off`：仅测试环境，还要额外确认，生产不要用；
- 已登记主机公钥变化时硬失败，页面不提供“一键覆盖”。

公钥变化先排查重装、换机、IP 复用或冒充，不要直接覆盖。

## 9. 知识库

导航“知识库”。

### 9.1 能看到什么

知识库统一收部署经验、排查报告、手工知识和上传文档。

列表可以按来源、标签、关键词筛选。详情里能看到正文、来源、关联任务和原文件。

如果任务报告下有人做过逐条反馈，知识正文末尾会多出“人工复核”一段，列出根因和每条结论的确认、否定或纠正内容；标签里也会出现“人工确认”“人工否定”或“人工纠正”。这段内容同样参与检索，下次排查时可能被引用。

![知识库：按类型、技术域、文件类型和时间筛选](images/09-知识库.png)

### 9.2 新增手工知识

点“新增手工知识”，填标题、正文、标签。

适合写：

- 稳定的排查顺序；
- 常见错误码和处理边界；
- 服务架构和依赖说明；
- 变更前的检查清单。

不适合写：

- 一次性密码、令牌；
- 未脱敏的客户数据；
- 没有验证过的猜测；
- 大段与运维无关的聊天记录。

### 9.3 上传文档

点“上传文档”，选择文件，填标题（默认用文件名）。

平台会抽取文字进入知识库，原文件保留在详情里可下载。上传后注意：

- 扫描件 OCR 可能有错，关键命令要人工核对；
- 大文档会分段入库，不代表整篇都能被一次召回；
- 涉及敏感信息的文档先脱敏；
- 上传成功不等于“已验证”，仍要在知识治理里审核。

### 9.4 知识治理

有权限的账号可以进“知识治理”。

治理动作包括：

- 看准入统计和待复核条目；
- 看“已放行”数量：这是按当前规则动态聚合出来的放行结果，不等于已经有一条可编辑知识；
- 打开一条记录，看来源、命中理由和当前决策；
- 改判为通过、复核或拒绝，并填写理由；
- 对处理失败的条目重新入队，让 worker 重判；
- 按来源、关键词和决策状态筛选。

治理页当前没有“合并重复条目、批量补标签、直接标记过期”的按钮；需要改知识正文或标签时，回到对应知识条目的编辑入口处理，不要把手改数据库当成治理流程。

自动报告只是候选，不会自动变成“已验证知识”。排查报告生成后，以及排查结束且结果为成功、采纳或部分完成时，都会进入知识聚合；任务结束不再等于知识消失。

### 9.5 RAG 怎么触发

平台不是每次对话都把知识库全塞给模型。当前规则：

- 明确问知识、问“以前怎么处理”时触发；
- 维护类意图（整理知识、删除条目等）不触发；
- 问题里出现错误码、端口、服务名等指纹时兜底触发；
- 每次最多带 2 条、约 2000 字、1 轮；
- 先关键词，关键词弱且存在手工/上传文档时才用向量兜底；
- 候选为空或只有自动报告时，不调用向量通道。

所以“知识库里有，但这次没被引用”不一定是故障，可能是问法不明确或预算收窄。需要时在问题里写清服务名、端口、错误码。

## 10. 告警

告警从 Alertmanager 进入 `POST /api/alerts/alertmanager`。

平台会做：

- Bearer 令牌校验；
- 请求体大小限制；
- 告警归一化、去重、风暴/抖动抑制；
- 按配置决定是否自动建只读排查任务；
- 通过飞书应用把告警文本发到目标群，并 @ 当前告警值班人；没有告警值班时回落到审批值班人，两类值班都为空时只发文本、不 @ 人。

注意：

- 新安装默认开启自动建单，只接 `critical`，主机白名单和告警名白名单都默认 `*`；
- `alert_auto_allow_hosts` 或 `alert_auto_allow_alertnames` 留空表示“不建单”，不是“不限”；要全部放行就填 `*`；
- 老环境如果数据库里已经存过 `false` 或空清单，升级后仍保持旧值，需要管理员在“配置 → 通知 → 告警自动建单”里手工保存一次；
- 面板里的“试一条告警”只判断规则，不建任务、不发通知；可先填主机、告警名和级别，看结果是“会建单”还是“不会建单”；
- 告警正文是不可信文本，只作为描述，不会变成系统指令；
- 告警任务只做只读排查，不生成部署计划、不申请执行许可；
- 同组已有未关闭任务时会复用，不重复建单。

操作时不要看到“监控告警”就当成“已确认故障”；先看报告证据。

## 11. 配置

导航“管理” → “配置”，只对管理员开放。页签：

| 页签 | 用途 | 注意 |
|---|---|---|
| 数据源 | Prometheus、日志、K8s、Docker 等连接和默认查询 | 先“测试连接”再启用 |
| 模型 | 模型厂商、地址、Key、模型名、预算 | Key 只写不读；测试连通后再用 |
| 主机配置 | 主机字段名、显示、顺序；密码集中管理 | 改字段会影响所有主机表单 |
| 用户与权限 | 建号、角色、密码、TOTP、手机号 | 删除是软删除，历史任务和审计保留 |
| 通知 | 飞书应用机器人、SMTP 邮件、告警自动建单、审批值班、告警值班、飞书身份绑定 | 先发测试卡片或测试邮件；告警范围先用“试一条告警”验证 |
| 外观 | 品牌名、背景等 | 不影响权限 |
| 设置 | 平台开关、主机公钥策略、允许网段和命令清单 | 改前确认影响范围 |

配置页的通知和设置按卡片分块，标题右侧有“收起 / 展开”。默认展开通知渠道和平台开关；飞书应用、告警自动建单、审批值班、告警值班、主机公钥校验、登录与访问默认收起，点按钮再展开。

### 11.1 飞书应用机器人

飞书入口统一走企业自建应用机器人，不再使用群 webhook。配置步骤：

1. 在飞书开放平台创建企业自建应用，启用机器人能力；
2. 开通发消息、读群成员、读用户基础信息和接收消息事件的权限，具体名称以飞书控制台当前版本为准；
3. 事件订阅选“长连接”，订阅消息事件 `im.message.receive_v1`，并开启卡片交互回调；
4. 在“配置 → 通知 → 飞书应用”填 App ID、App Secret 和目标群 `chat_id`，多个群用逗号分隔；
5. 点“读取机器人所在群”选择群，保存后确认页面显示“长连接已连接”；
6. 点“发测试卡片”，卡片能到群说明凭据、群和发消息权限都通了；
7. 在“飞书身份绑定”读取群成员，把成员绑到平台账号。

注意：

- App Secret 只写不读，保存后页面只显示“已配置”；
- 机器人只处理目标群的消息，拉到其他群不会变成公共查询入口；
- 飞书身份可以绑定任意启用用户，用于接收 @；审批按钮只认绑定到管理员账号的人；
- 长连接断开时，卡片和群命令都收不到，先看页面状态和 `logs/feishu_ws.log`；
- 群成员能看到机器人的回复，不要在群里发密码、TOTP、模型 Key 或客户数据。

### 11.2 审批值班和告警值班

| 值班类型 | 谁可以排 | 负责什么 | 没有值班人时 |
|---|---|---|---|
| 审批值班 | 仅管理员 | 接收待审批和超时提醒，配合卡片审批 | 回落到全体启用管理员 |
| 告警值班 | 任意启用用户 | 接收告警文本和被 @ | 回落到审批值班；审批值班也为空时不 @ 人 |

值班只影响“通知发给谁”，不改变审批权限。能点“批准 / 驳回”的仍然是绑定到管理员账号的飞书成员。

### 11.3 飞书里收到的内容

- 审批：卡片带“批准 / 驳回 / 打开平台”按钮；高危命令的批准按钮会再弹一次确认。
- 排查：文本只保留结论、第一条直接根因和前 3 步处置方案，避免刷屏。
- 部署：文本带部署命令清单，命令来自部署方案的 `operations`，不包含预检和回滚步骤。
- 告警：文本带告警名、级别、主机和摘要，并 @ 当前告警值班人。
- 状态色标：🔵 排查或状态、🟢 成功或恢复、🟡 部分成功、🔴 失败或告警、🚫 驳回、🔔 评论、📌 转派。

飞书纯文本不能改气泡背景色，也不能改字体颜色；上面这些是文字前的状态色标，不是卡片背景。

### 11.4 群里 @机器人 能做什么

只支持下面这些固定命令，不支持自由聊天。

| 命令 | 作用 | 权限和注意 |
|---|---|---|
| `/状态` | 查看最近 6 条有权限看的任务 | 需要先绑定平台账号 |
| `/状态 任务号` | 查看一条任务的状态、提交人、处理人和任务号 | 只能看自己可见范围内的任务 |
| `/重跑排查 任务号` | 立即创建一条新的排查任务，按实际 token 计费 | 仅管理员、排查员、值班工程师；没有二次确认 |
| `/帮助` | 返回命令菜单 | 任何人可用 |

使用规则：

- 必须在配置的目标群里，并且 @机器人，或者命令以 `/` 开头；
- 私聊机器人暂不处理；
- 同一条飞书事件重复投递只处理一次，不会重复建任务；
- 重跑只支持排查任务，部署任务请回平台处理；
- 正在提交、进行中、待审批或执行中的任务不能重跑；
- 重跑会立即提交新任务并调用大模型，按实际 token 计费；群里误发或重复发都会产生费用；
- 任务号是 36 位 UUID；`/状态` 不带任务号时只列任务号，不展开每条详情。

### 11.5 通知里的“查看”链接

通知末尾的链接前缀取 `NOTIFY_BASE_URL`，没配时用 `FRONTEND_URL`，再没有就落到 `http://127.0.0.1:5173`。

如果前缀是本机地址，飞书手机或同事的电脑点不开。这不影响审批按钮和群命令；需要看详情时，把消息里的任务号复制到平台搜索即可。以后平台部署到内网地址或域名，再配置 `NOTIFY_BASE_URL`。

![配置页数据源：启用/停用、健康状态、检查和编辑入口](images/10-配置-数据源.png)

数据源和模型密钥在数据库加密存储，页面不回显明文。写入新密钥需要当前管理员 TOTP。

不要：

- 把 root 凭据当应用长期凭据；
- 在数据源地址里写明文密码；
- 为了让连接成功关闭 TLS 校验；
- 把模型 Key 写进任务描述或评论。

## 12. 审计

导航“审计”，按时间倒序展示。

![审计流水：按事件、操作人、排查号和 trace 查询](images/12-审计流水.png)

可以按：

- 关键词；
- 时间范围；
- 操作人；
- 排查号 / `trace_id`；
- 事件类型；

筛选，点一行展开 payload。payload 已按敏感键剔除，仍要按最小必要原则查看和导出。

常用动作：

- **按本 trace 筛选**：看一条任务从提交、排查、审批到执行的完整链路；
- **导出 CSV**：导出当前筛选命中的流水，注意后端会返回行数和截断标记。

审计导出可能包含内部标识和操作细节，不要发到无关群聊。

## 13. 数据库迁移

升级到包含评论线索、逐条报告反馈、飞书应用和告警值班的版本时，先备份数据库，再按顺序执行七个迁移。

在 `code` 目录下，用后端虚拟环境的 Python 执行：

```powershell
python backend/scripts/apply_migration.py backend/migrations/038_task_comment_clues.sql
python backend/scripts/apply_migration.py backend/migrations/039_report_feedback.sql
python backend/scripts/apply_migration.py backend/migrations/040_oncall_shifts.sql
python backend/scripts/apply_migration.py backend/migrations/041_feishu_card_approval.sql
python backend/scripts/apply_migration.py backend/migrations/042_feishu_multi_chat.sql
python backend/scripts/apply_migration.py backend/migrations/043_oncall_alert_scope.sql
python backend/scripts/apply_migration.py backend/migrations/044_feishu_event_update.sql
```

七个迁移的作用和回滚影响：

| 迁移 | 作用 | 回滚影响 |
|---|---|---|
| `038_task_comment_clues.sql` | 给 `v3_task_comments` 增加 `kind` 列，区分普通讨论和排查线索 | 删除 `kind` 列，所有历史评论都会回到普通讨论，线索不再进入 Agent |
| `039_report_feedback.sql` | 新建 `v3_report_feedback`，保存根因和逐条结论反馈 | 删除反馈表，已有反馈记录全部丢失 |
| `040_oncall_shifts.sql` | 新建 `v3_oncall_shifts`，保存审批值班安排 | 删除值班表，已有值班记录全部丢失 |
| `041_feishu_card_approval.sql` | 新建飞书身份绑定表和卡片事件去重表 | 删除两张表，飞书身份绑定和回调记录全部丢失，需要重新绑定 |
| `042_feishu_multi_chat.sql` | 把旧单群 `chat_id` 搬成 `chat_ids` 数组 | 收回单群，只保留第一个群，其他群的审批卡片不再发送 |
| `043_oncall_alert_scope.sql` | 值班拆成 `approval` 和 `alert`，并删除旧群 webhook 配置 | 恢复为只允许审批值班；需先删除告警值班记录，旧 webhook 配置不会恢复 |
| `044_feishu_event_update.sql` | 给应用账号补飞书事件表的 `UPDATE` 权限，允许回写结果和任务号 | 收回 `UPDATE`，事件仍能插入，但结果状态无法补写 |

回滚按相反顺序执行，执行前先导出相关数据：

```powershell
python backend/scripts/apply_migration.py backend/migrations/044_feishu_event_update.rollback.sql
python backend/scripts/apply_migration.py backend/migrations/043_oncall_alert_scope.rollback.sql
python backend/scripts/apply_migration.py backend/migrations/042_feishu_multi_chat.rollback.sql
python backend/scripts/apply_migration.py backend/migrations/041_feishu_card_approval.rollback.sql
python backend/scripts/apply_migration.py backend/migrations/040_oncall_shifts.rollback.sql
python backend/scripts/apply_migration.py backend/migrations/039_report_feedback.rollback.sql
python backend/scripts/apply_migration.py backend/migrations/038_task_comment_clues.rollback.sql
```

`043` 回滚前必须先清理告警值班记录，否则约束加不上：

```sql
DELETE FROM v3_oncall_shifts WHERE scope = 'alert';
```

迁移后核对：

```sql
\d v3_task_comments
\d v3_report_feedback
\d v3_oncall_shifts
\d v3_feishu_identities
\d v3_feishu_events
```

确认 `v3_task_comments.kind` 存在，四张新表存在，`v3_oncall_shifts.scope` 允许 `approval` 和 `alert`，并确认应用账号对新表有 `SELECT`、`INSERT`、`UPDATE` 权限。飞书事件表只需要 `SELECT` 和 `INSERT`。

## 14. 常见操作问题

| 现象 | 可能原因 | 怎么做 |
|---|---|---|
| 提交后一直“已提交” | worker 没起来或队列没被领取 | 找运维看 worker 和队列 |
| 一直“进行中” | worker 卡住、租约过期、数据源慢 | 看“过程与参考”，找运维看队列租约 |
| 报告没有结论 | 数据源缺失、目标不清、证据不足 | 补数据源或重新描述，不要直接批准执行 |
| 报告写“无数据” | 没查到，不是正常 | 补目标/数据源后重查 |
| 知识库有但没被引用 | 问法不明确或 RAG 预算收窄 | 在问题里写服务名、端口、错误码 |
| 数据源测试失败 | 地址、凭据、网络、TLS | 先修连接，不要绕过校验 |
| 主机执行被拒绝 | 主机未登记、未确认公钥、策略 strict | 登记主机并确认密钥 |
| 审批按钮灰色 | 不是管理员、方案过期、职责分离 | 换审批人或重新生成方案 |
| 飞书没有收到通知 | 应用未启用、长连接断开、群没选中、机器人被移出群 | 看配置页状态和 `logs/feishu_ws.log`，补选群后重发测试卡片 |
| 群里 @机器人 没反应 | 不在目标群、只私聊、没 @机器人、命令写错、账号没绑定 | 到目标群按 `/帮助` 的写法重发，先完成飞书身份绑定 |
| 点“批准”提示没权限 | 飞书账号绑到了普通用户，不是管理员 | 换绑定到管理员的飞书账号，或让管理员在平台审批 |
| 重跑被拒绝 | 角色不够、任务不是排查、任务还在处理中 | 换有权限的账号，等任务结束后再重跑 |
| 飞书里的“查看”打不开 | 链接前缀是本机 `127.0.0.1` | 复制任务号到平台搜索，或部署到可访问地址后配 `NOTIFY_BASE_URL` |
| 执行结果失败 | 命令退出码非 0、目标不可达 | 看输出和审计，人工核对后重新发起 |
| 部署方案不能确认 | 不是提交人、方案过期 | 让提交人确认或重新生成 |

## 15. 安全红线

1. 不把密码、TOTP、模型 Key、Webhook 令牌写进任务描述、评论、知识库或截图。
2. 不绕过审批直接执行；不借别人的账号批准。
3. 不为了让任务“跑通”而关闭主机公钥校验、审计或凭据加密。
4. 不把“AI 预审低风险”当人工批准。
5. 不把“报告已完成”当“已采纳”或“已修复”。
6. 不把“无数据”当“正常”。
7. 不在生产上测试不确定的命令；先用只读命令和测试主机验证。
8. 不覆盖已登记主机公钥；先排查变化原因。
9. 不删除审计对象来“清理空间”；保留策略是合规要求。
10. 不把审计导出、报告原文和客户数据发到无关群聊。
11. 不把飞书 App Secret、验证令牌、加密密钥写进代码、文档或群消息。
12. 不把运维机器人拉进无关群；群成员能看到命令回复，按最小范围建群。
13. 不在飞书群里发密码、TOTP、模型 Key 或带凭据的命令输出。
